## 1. What this is, in four sentences

`themis_assess` is a Python library that takes a **fitted model plus a test set** and
answers three questions: how accurate is it, how much accuracy does it lose when the data
shifts, and **is either answer good enough for the deployment you have in mind**. The third
question — acceptance thresholds and degradation tolerances — is the part most evaluation
code omits, and it is the reason the library exists.

It is task-agnostic (classification and forecasting today; plain regression and count
outcomes are *not* covered and may error) and framework-agnostic: a model becomes
assessable by wrapping it in a ~5-line handler. The core depends only on numpy, pandas,
scikit-learn, scipy, plotly and pyyaml; everything heavier (darts, transformers, shap,
safetycage) is an extra, imported lazily inside the one module that needs it.

Provenance: EU Horizon Europe project **THEMIS 5.0** (grant 101121042, 2023–2026), SINTEF
Digital. The methodology follows Michałowska & Johnsen, *Evaluating Machine Learning
Robustness Under Natural Distribution Shifts* (SINTEF Digital, 2026) — referred to
everywhere in the code simply as **"the survey"**, with §-numbers that are load-bearing:
a docstring saying §5.1.3 means the reader can find the equation.

## 3. The mental model

Data and model enter through **contracts**; everything downstream is written against the
contracts and knows nothing about your model.

```
your model ──► handlers/   (ModelHandler → Prediction, declares AccessLevel)
your data  ──► core/       (DataAdapter → (n_entities, n_timesteps, n_features))
                   │
     ┌─────────────┼──────────────┬──────────────────┐
 perturbations/  metrics/      protocols/            │
 18 shifts ×     61 specs +    6 split protocols     │
 severity 1–5    catalog       (survey §3.1)         │
     └─────────────┴──────────────┘                  │
                   ▼                                 │
            assessment/   AccuracyEvaluator → AccuracyResult (+verdict)
                          RobustnessEvaluator → RobustnessAssessment (+verdict)
                          criteria.py / tolerance.py = the thresholds
                   ▼
  sensitivity/ · attribution/ · comparison/ · viz/ · summary/
                   ▼
            report/   one dict · ranked findings · survey §8 rules
```

Six ideas you must hold to read the code at all:

- **The canonical shape.** Every adapter presents data as `(n_entities, n_timesteps,
  n_features)`. Tabular data has a singleton time axis; ragged sequences are NaN-padded and
  carry a `valid_mask()`. This is why a perturbation written for time series also works on
  a table — do not add a second shape.
- **Access level** (`BLACK_BOX < PROBABILISTIC < QUERY < EMBEDDING < GRADIENT <
  ARCHITECTURE`). A handler *declares* what it can produce; the library checks the promise
  and `.plan()` reports which metrics are consequently unavailable **before** a long run.
- **Severity** is an ordered axis 1–5, not a physical unit. Numeric magnitudes are
  *relative* to each feature's own standard deviation, so severity 3 means something
  comparable across features in different units.
- **Three-valued verdicts.** `passed` is `True`, `False` or `None`. `None` means nothing
  was checked and is **not** a pass. An assessment without criteria must never read as
  approval (survey §8).
- **Tolerance basis.** A degradation tolerance is read as `aggregate`, `worst_perturbation`
  or `worst_cell`. The three genuinely disagree, so the basis is part of the requirement.
- **Relative never travels alone.** A robustness metric states what was *lost*; it is
  meaningless without the absolute clean and perturbed values, which is why
  `RobustnessResult` carries them and `check_report` complains when they are missing.

## 5. The layer the README does not mention

`src/themis_assess/summary/` is exported (`summarise`, `Summary`, `Audience`), tested
(`tests/summary/`), and documented in DECISIONS **D62–D68** — but it has no README section.
Do not assume it is dead code.

It turns a report into prose in three parts, only one of which uses a language model:

1. **templates.py** — deterministic sentences with the numbers substituted. Nothing is
   generated, so nothing can be invented. This is the shippable fallback.
2. **narrative.py** — an optional *local* model (e.g. `OllamaModel`) groups findings into
   themes and phrases them for a reader. Its output is checked by **verify.py** and
   discarded on failure, so a model can improve the summary or leave it unchanged, never
   make it wrong.
3. **actions.py / actions.yaml** — recommendations are *retrieved* from a human-written
   catalogue, never authored by a model. What to do about a weak model is knowledge about
   the deployment, and a model asked to invent it produces fluent, unfounded advice.

`audience.py` (clinician / manager / ML engineer) shapes the templates as well as the
prompt, which is what keeps the model genuinely optional. `Summary.provenance` always
records which path wrote the prose. Example usage: `examples/try_summary.py`.

## 6. Running things on **this machine** (Windows)

`python` on PATH is the Microsoft Store stub and does not work. The environments are
miniforge conda envs:

| Env | Python | Has | Use for |
|---|---|---|---|
| `themis-assess-312` | 3.12.15 | pytest, pandas 3.0.6, **no darts** | the general dev env |
| `themis-assess-forecast` | 3.12.15 | pytest, **darts 0.48.1**, numpy 2.5.4, pandas 2.3.3, scipy 1.18.1, sklearn 1.9.1 | the full suite, the forecasting tutorial |
| `themis-assess` | 3.15 | neither pytest nor the package | ignore it |

**The trap that costs an afternoon:** invoking an env's `python.exe` by full path
*without activating the environment* crashes inside any LAPACK call —
`Windows fatal exception: code 0xc06d007f`, usually surfacing in `scipy.linalg.lstsq` under
a `sklearn` `.fit()`. MKL's DLLs live in the env's `Library\bin`, which only activation puts
on `PATH`. numpy imports fine, so it presents as a broken library rather than a broken
invocation. DECISIONS.md records this under "Still to be tested, not decided".

Use `conda run`, which activates:

```powershell
$conda = "C:\Users\paljo\AppData\Local\miniforge-pypy3\Scripts\conda.exe"
& $conda run -n themis-assess-forecast python -m pytest          # full suite
& $conda run -n themis-assess-forecast python -m pytest tests/report
& $conda run -n themis-assess-forecast ruff check src tests tools
& $conda run -n themis-assess-forecast python tools/sync_requirements.py --check
```

Verified 2026-11-04 in `themis-assess-forecast`: **1424 passed, 1 skipped in 76 s**
(1406 collect in `themis-assess-312`, where the darts integration tests skip at import).
Note `addopts = "-q"` is already in `pyproject.toml` — passing another `-q` makes it `-qq`
and silently suppresses the final summary line.

**A second trap:** the editable install in these envs points at the *other* checkout (see
§8), so a bare `import themis_assess` from a script or notebook may import
`C:\Users\paljo\Documents\themis-accuracy-robustness\src`, not this tree. `pytest` is
unaffected — `pyproject.toml` puts this repo's `src/` first. For anything else, set
`PYTHONPATH` to this repo's `src` explicitly, or re-point the install:
`pip install -e . --no-deps`.

## 7. House rules — the invariants a change must not break

These are enforced by tests, by CI, or by the design. Breaking one silently is the failure
mode the repo is built to prevent.

1. **A metric is three things.** A callable in `metrics/accuracy/catalog.py`, a `MetricSpec`
   in `metrics/registry.py` (direction, bounds, tasks, access, survey reference), and a
   sentence in `metrics/glossary.py`. Tests assert catalog ⊆ registry and glossary ↔
   registry, so a metric cannot be computable-but-unregistered or registered-but-undescribed.
2. **Requirements files are generated.** `pyproject.toml` is the single source of truth.
   After any dependency change run `python tools/sync_requirements.py`;
   `tests/test_requirements.py` and a CI job fail when the five generated files are stale.
3. **The core never imports an extra.** darts, transformers, shap, safetycage and
   statsmodels are imported *inside* the function that needs them, with an error naming the
   extra. A child-process test pins this.
4. **Randomness comes from the handed-in `rng`, never global numpy state.** That is what
   makes a recorded seed reproduce one cell of a sweep (`core/seeding.derive_seed`; D31 —
   an earlier revision used `hash()`, which randomises per process).
5. **Figures are pure.** A builder in `viz/figures.py` is a function of a result object:
   no model calls, no statistical tests. If an analysis must run first, the pair belongs in
   `viz/bundles.py` and returns `Bundle(figure=..., analysis=...)` (D44). No figure carries
   two y-scales, and a test enforces it.
6. **Survey names are canonical, with no aliases** (D19). The library should read like the
   paper.
7. **Verdicts stay three-valued** (§3). Never collapse `None` into `False` or `True`.
8. **Provenance survives.** Ported symbols carry a docstring line saying where they came
   from; `AssessmentReport` records how every number was produced.
9. **Tests are named after the property they defend**, not the function they call —
   `test_the_baseline_improvement_is_sign_corrected`, not `test_improvement_over_baseline`.
   Several exist because the behaviour they pin was once wrong, and the docstring says so.
10. **Style:** ruff, line length 100, target py311, floor `>=3.11`. Prose in docstrings and
    docs explains *why*, usually by naming the alternative that was rejected — match that
    register when you edit them.

## 10. Recipes

| Task | Do this |

| Add a metric | callable → `metrics/accuracy/catalog.py`; `MetricSpec` → `metrics/registry.py`; sentence → `metrics/glossary.py`. README "A new metric" has the full snippet. |

| Add a finding or a §8 rule | generator in `report/findings.py` / check in `report/rules.py`; every one needs a stable `rule` id, its evidence, and a suggestion. |
| Change a dependency | edit `pyproject.toml`, then `python tools/sync_requirements.py`. |
| Rebuild a tutorial | `python docs/build_tutorial.py` (classification) / `python docs/build_solar_forecasting_tutorial.py` (forecasting) — each executes every cell and fails loudly, which is what keeps the prose honest (D57), and each refuses to overwrite hand edits (D78). Needs an activated env. |
| Publish the tutorials as a web page | `python tools/build_docs_site.py` writes `site/` from the **committed** notebooks — nbconvert only, nothing is executed. `.github/workflows/pages.yml` does the same on a push to `main` and deploys to GitHub Pages. |
| Understand why something is as it is | `docs/DECISIONS.md`, D1–D73. Search it before proposing a redesign. |

## 11. Known-open questions

From the end of `DECISIONS.md`, still unresolved:

- **darts + pandas 3.x** is untested. `themis-assess-forecast` pins `pandas<3` deliberately;
  `themis-assess-312` has pandas 3.0.6 but no darts. Start from the 312 env if you resolve it.
- **Python 3.13 + darts** untried — 3.13 is the interesting number because `safetycage`'s
  floor is ≥3.13, and whether `[timeseries]` and `[safetycage]` can coexist in one
  environment depends on it.
- Regression (continuous outcomes) and count/Poisson outcomes are **not** covered by the
  library; the README says so, and an attempt may error rather than warn.
